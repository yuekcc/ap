# 5. 写一条清楚的任务

ap 不会读心。任务写得越具体，它越少走弯路。一条好任务通常包含四块：

```text
目标：要完成什么。
范围：允许看哪些文件、改哪些文件。
约束：不能做什么，必须遵守什么。
验收：怎么判断做完了。
```

不要求每次写满四块，但至少把目标和验收说清楚。

## 三种提示词来源

一次运行必须且只能给一个来源。

```sh
# 直接写在参数里
./build/ap --print "解释 ap-core/engine/loop.odin 的状态机"

# 从 UTF-8 文件读取
./build/ap --input-file prompt.txt

# 从 stdin 读取，读到 EOF 为止
cat prompt.txt | ./build/ap --print0
```

`--print0` 里的 `0` 表示 fd 0，也就是 stdin，不是 NUL 分隔。ap 不会根据 stdin 是不是终端来隐式读取，必须显式写 `--print0`。

三个同时出现会按用法错误退出 2。一个都不给也会退出 2。`--help`、`--version`、`--list-skills` 和 `--print-system-prompt` 不需要提示词。

## 把长材料交给 ap

长材料用 `--input-file` 或 `--print0`，不要硬塞进命令行。Windows 的命令行长度限制更紧。

提示词文件里可以写：

```text
目标：修复登录页在窄屏下的横向滚动。

范围：
- 只看 ap-web/frontend/ 下的样式和组件。
- 不要改后端协议。

约束：
- 保持现有配色。
- 不引入新的前端依赖。

验收：
- 宽度 320px 时没有横向滚动。
- npm --prefix ap-web test 通过。
```

## 让 ap 读取图片

图片输入默认关闭。打开配置：

```json
{
  "image_input": true
}
```

然后把图片路径写进任务。ap 的 `read_file` 能识别 PNG、JPEG、GIF 和 WebP，把原图作为附件交给模型。SVG 仍按文本文件读取。

限制：

- 单张图片默认不超过 5 MiB，由 `image_max_bytes` 控制。
- ap 不缩放、不转码、不处理 EXIF 旋转。
- 模型必须支持视觉输入，否则请求可能被拒绝。

## 好任务与坏任务

**坏任务：**

```text
帮我优化一下这个项目。
```

问题：不知道优化什么，不知道能不能改文件，也不知道什么算完成。

**好任务：**

```text
目标：减少 ap-cli/options.odin 里重复的参数解析分支。

范围：只改 ap-cli/options.odin 和对应测试。

约束：不改变现有参数名和行为。

验收：./test.sh 通过；新增或修改的测试覆盖至少两个参数。
```

问题少了，验收清楚了，ap 才知道什么时候停。

## 几条实用规则

- 一次只给一个目标。多个不相关的任务拆成多轮。
- 告诉它怎么验证。能跑测试就写测试命令，能看页面就写页面路径。
- 明确“只读”还是“可以改”。不确定时先让它调查，再让它动手。
- 不要粘贴真实密钥、令牌或客户隐私。模型看到的文本会进入 transcript。
- 需要它先调查再修改时，直接写“先给出方案，等我确认后再改”。ap 没有 plan mode，但这句会改变它的行为。
- 失败时把完整报错贴回去，不要只说“还是不行”。
