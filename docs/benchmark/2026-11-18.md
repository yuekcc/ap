## 4. 优化效果对比

### 4.1 修复方案

四者都从同一个父提交 `e5575ba` 出发，但修法不同：

| 点 | AP-1 | AP-2 | AP-3 | Pi |
| --- | --- | --- | --- | --- |
| 根因处理 | 拆 `loop_release_owned` → `loop_release_message_id` + `loop_release_calls`；`loop_own_calls` 只释放 calls | 调整 `Provider_Message_End` 顺序：先写 `message_end`，再 `loop_own_calls`；`loop_release_owned` 同步清空 `current_message_id` | 去掉 `owned_message_id`，让 `current_message_id` 成为唯一属主；拆 `loop_release_message_id` / `loop_release_calls`，在 `message_end` 落盘后释放 id | 拆 `loop_release_owned` → `loop_release_calls`；`loop_own_calls` 只释放 calls |
| 消息 id 写入 | 新增 `loop_set_message_id`（先释放、再 clone、再让 current 别名 owned） | 没有新入口；`Provider_Message_Start` 仍是 `delete` + `clone` | `current_message_id` 自己就是属主；`Provider_Message_Start` 只在 `!message_started` 时 clone | 新增 `loop_own_message_id`（clone 早于 delete） |
| 无 provider id | 改用 `uuid.to_string_buffer` 栈缓冲，再 clone 给 owned | **未修**，只在报告里指出每条消息泄漏 36 字节 | uuid 字符串归 `current_message_id`，由 `loop_release_message_id` 释放 | 生成的 uuid 直接赋给 `owned_message_id` |
| `message_end` 补 id | 未专门处理（start 已生成 uuid，保持 current） | 未专门处理 | 未专门处理；用 `!message_started` 守卫保证 start/end 一致 | `current` 为空时才用 `ev.message_id` 补齐 |
| 别名失效 | `loop_release_message_id` 里清空 current | `loop_release_owned` 里清空 current | 没有别名，只有一个属主 | 依赖调用点在释放前先清空 current |
| 防御性 | 所有权集中，注释清楚；但“先释放再 clone”对 self-alias 有潜在风险 | 改动最小；顺序约束靠注释和测试守住，未来重排仍可能复发 | 模型最简单：单一属主 + 明确的释放时机；取消路径的 id 要等到下一次 reset 才释放 | clone-before-delete + end-id 补齐，防御点最多 |
| 文档 | 修改 architecture + react-loop | 无 | 只修改 architecture | 修改 architecture + react-loop |

实现细节上：

- **AP-1** 的 `loop_set_message_id` 把“释放 + clone”集中到一个入口，所有权模型集中、注释清楚；但它是“先释放旧值，再 clone 新值”，如果未来某个调用把 `owned_message_id` 本身传回来，会有 self-alias 风险。当前调用点不会触发。
- **AP-2** 的修法最小：它没有拆释放职责，而是保证“写 `message_end` 发生在 `loop_own_calls` 之前”，并把 `current_message_id` 的别名在 `loop_release_owned` 里一起清掉。当前代码正确，测试也能抓住回归；但“必须先写后收养”是一个顺序不变量，不像 AP-1/AP-3/Pi 那样由所有权拆分或单一属主从结构上消除。
- **AP-3** 的方案最彻底：`current_message_id` 从“别名”变成唯一属主，`owned_message_id` 整个删除；`loop_release_message_id` 只在 `message_end` 落盘之后（以及 reset/destroy）释放。它顺带修掉了 uuid 泄漏，并加了 `!message_started` 守卫，避免 `message_start` 落盘后又被 provider 的 id 改掉。代价是取消路径的 id 不会立刻释放，要等到下一次 `loop_reset_attempt` 或 `loop_destroy`；这是有界的，不是永久泄漏。
- **Pi** 的 `loop_own_message_id` 明确“clone 早于 delete”，并为 `Message_End` 补了“current 为空才采纳 end id”的分支，防御点最多；代价是多一个函数和一点分支逻辑。

四者的共同点：都保证 `message_end` 落盘时 `message_id` 仍然有效，`message_start` / `message_end` 的 id 重新一致。AP-1/AP-3/Pi 从所有权层面拆开了 message id 与 tool call 的释放；AP-2 靠“先写后收养”的顺序约束和 alias 清空来保证。

### 4.3 对运行时行为/性能的影响

四者的代码改动都只在 `ap-core/engine/loop.odin` 和测试；AP-1/Pi/AP-3 还同步了文档。不涉及协议和前端：

- `message_end` 路径不再读已释放的 `message_id`，transcript 中 `message_start` / `message_end` 的 id 重新一致，修复了 Web 端 `hadDelta[messageId]` 查不到、可能重复追加气泡的问题。
- AP-1、AP-3、Pi 顺带修掉了 provider 不返回 id 时的每条消息泄漏：AP-1 用栈缓冲 + owned 持有，AP-3 让生成的 uuid 归 `current_message_id` 并由 `loop_release_message_id` 释放，Pi 用 owned 持有。
- AP-2 **没有修**这个泄漏：`loop_start_message` 生成的 uuid 仍然只挂在 `current_message_id` 上，`message_end` 后直接清空，没有 `delete`。provider 不返回 `message_id` 时，每条 assistant 消息仍泄漏 36 字节。
- AP-3 删除了 `Loop.owned_message_id` 字段；全仓没有其他引用，不涉及外部 API 或协议。
- AP-3 的取消路径（`loop_write_cancelled_message`）不会立即释放 id，要等到下一次 `loop_reset_attempt` 或 `loop_destroy`；这是有界的，不是永久泄漏。
- AP-3 的改动不新增分配，alias 清空/单一属主的释放是 O(1)；AP-1 的栈 uuid 少一次堆分配；Pi 的 owned uuid 多一次 clone，但会在释放路径回收。
- 四者都没有可测量的性能回归，也没有新增依赖或协议字段。

### 4.4 遗留问题

- **AP-1** 在报告里额外指出两个预存在问题：
  1. 自定义 `context.allocator` 下 `json.destroy_value` 处理 `json.Object` 会崩，导致回归测试无法覆盖工具调用；
  2. `ODIN_TEST_TRACK_MEMORY=true` 时 `test_loop_blobs_large_tool_output` 会报 `bad free`，疑似 fake provider 的 args 树与销毁 allocator 不匹配。
- **AP-2** 额外指出 uuid 泄漏，并询问是否一起处理；但没有修。日志里还探索了一个“污染 7 字节 free 会段错误”的异常，最终判断为堆布局/地址复用伪影并放弃，**没有写进最终报告**。这不是本次 UAF 的结论，但说明它的核实阶段有一次未收敛的支线。
- **AP-3** 修掉了 uuid 泄漏，并给出 `message_start` / `message_end` 一致性守卫；但它只更新了 `docs/internal/architecture.md`，没有同步 `docs/internal/react-loop-and-session.md` 里“同一条消息的 start/end 用同一个 id”的约定（AP-1/Pi 补了这句）。它也没有覆盖自动生成 id 的回归测试，代码未提交。取消路径的 id 延迟释放属于有界行为，不是永久泄漏。
- **Pi** 没有继续追这两个预存在问题，但它的测试已经覆盖 tool call 路径，实际修复的验证更完整。

## 6. 总结

四个运行最终都正确修掉了同一个 UAF，差异主要在过程效率、测试覆盖和修复完整性：

- **AP-3 的优势**：有效工作 226.0s、47 次工具、1.68M tokens，三项都是四者最低；修复阶段 111.2s 也是最快。修法最彻底：`current_message_id` 单一属主，顺带修掉 uuid 泄漏，并加了 start/end 一致性守卫。**本次综合最好。**
- **Pi 的优势**：回归测试覆盖最广（provider id、自动生成 id、tool call）；防御点最多（clone-before-delete、end-id 补齐）；代码已提交、文档同步完整。**如果看回归覆盖和提交/文档完整度，Pi 更好。**
- **AP-1 的优势**：核实最快（90.5s）；动态证明直接；报告额外指出两个预存在问题；文档对单一属主模型的描述更集中。**如果看核实证据和报告完整度，AP-1 最好。**
- **AP-2 的教训**：52s 就拿到证据，却被一个次要 allocator 异常多拖了约 138s；回归测试只覆盖 provider id；uuid 泄漏只报告未修；文档未同步；而且它把“核实一下”自行扩展成了修复，用户没有确认机会。

三个 AP 运行说明单次样本的方差很大：同一个模型、同一套工具，AP-1/AP-2/AP-3 的有效工作是 480.4s / 357.0s / 226.0s，tokens 是 5.30M / 2.70M / 1.68M。主要差别看起来是过程纪律：AP-3 用 `read_file` 建立图景、在拿到确定性证据后停止探索、正式改动只用一次 `edit_file`，因此同时赢在时间、工具和 token。但 AP-3 的英文 system prompt 和不同的工作区也是未剥离的变量，不能把差异全部归因于过程纪律。

如果以 **“用最少的时间和 token 得到正确且可回归的修复”** 为标准，本次对比 **AP-3 最好**；如果以 **“回归覆盖 + 提交/文档完整度”** 为标准，**Pi 更好**；如果以 **“核实证据的充分性和报告的完整性”** 为标准，**AP-1 更好**。
