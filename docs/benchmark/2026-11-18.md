## 4. 优化效果对比

### 4.1 修复方案

三者都从同一个父提交 `e5575ba` 出发，但修法不同：

| 点 | AP-1 | AP-2 | Pi |
| --- | --- | --- | --- |
| 根因处理 | 拆 `loop_release_owned` → `loop_release_message_id` + `loop_release_calls`；`loop_own_calls` 只释放 calls | 调整 `Provider_Message_End` 顺序：先写 `message_end`，再 `loop_own_calls`；`loop_release_owned` 同步清空 `current_message_id` | 拆 `loop_release_owned` → `loop_release_calls`；`loop_own_calls` 只释放 calls |
| 消息 id 写入 | 新增 `loop_set_message_id`（先释放、再 clone、再让 current 别名 owned） | 没有新入口；`Provider_Message_Start` 仍是 `delete` + `clone` | 新增 `loop_own_message_id`（clone 早于 delete） |
| 无 provider id | 改用 `uuid.to_string_buffer` 栈缓冲，再 clone 给 owned | **未修**，只在报告里指出每条消息泄漏 36 字节 | 生成的 uuid 直接赋给 `owned_message_id` |
| `message_end` 补 id | 未专门处理（start 已生成 uuid，保持 current） | 未专门处理 | `current` 为空时才用 `ev.message_id` 补齐 |
| 别名失效 | `loop_release_message_id` 里清空 current | `loop_release_owned` 里清空 current | 依赖调用点在释放前先清空 current |
| 防御性 | 所有权集中，注释清楚；但“先释放再 clone”对 self-alias 有潜在风险 | 改动最小；顺序约束靠注释和测试守住，未来重排仍可能复发 | clone-before-delete + end-id 补齐，防御性最好 |
| 文档 | 修改 architecture 所有权段落 + react-loop 一句 | 无 | architecture 新增第 5 条 + react-loop 一句 |

实现细节上：

- **AP-1** 的 `loop_set_message_id` 把“释放 + clone”集中到一个入口，所有权模型最集中、注释清楚；但它是“先释放旧值，再 clone 新值”，如果未来某个调用把 `owned_message_id` 本身传回来，会有 self-alias 风险。当前调用点不会触发。
- **AP-2** 的修法最小：它没有拆释放职责，而是保证“写 `message_end` 发生在 `loop_own_calls` 之前”，并把 `current_message_id` 的别名在 `loop_release_owned` 里一起清掉。当前代码正确，测试也能抓住回归；但“必须先写后收养”是一个顺序不变量，不像 AP-1/Pi 那样由所有权拆分从结构上消除。
- **Pi** 的 `loop_own_message_id` 明确“clone 早于 delete”，并为 `Message_End` 补了“current 为空才采纳 end id”的分支，防御性更强；代价是多一个函数和一点分支逻辑。

三者的共同点：都保证 `message_end` 落盘时 `message_id` 仍然有效，`message_start` / `message_end` 的 id 重新一致。AP-1 和 Pi 进一步把 message id 与 tool call 的释放拆开，从结构上消除这条路径；AP-2 则靠“先写后收养”的顺序约束和 alias 清空来保证。

### 4.3 对运行时行为/性能的影响

三者的代码改动都只在 `ap-core/engine/loop.odin` 和测试；AP-1/Pi 还同步了文档，不涉及协议和前端：

- `message_end` 路径不再读已释放的 `message_id`，transcript 中 `message_start` / `message_end` 的 id 重新一致，修复了 Web 端 `hadDelta[messageId]` 查不到、可能重复追加气泡的问题。
- AP-1 和 Pi 顺带修掉了 provider 不返回 id 时的每条消息泄漏：AP-1 用栈缓冲 + owned 持有，Pi 用 owned 持有。
- AP-2 **没有修**这个泄漏：`loop_start_message` 生成的 uuid 仍然只挂在 `current_message_id` 上，`message_end` 后直接清空，没有 `delete`。它自己也在报告里指出了这一点，但没有改。provider 不返回 `message_id` 时，每条 assistant 消息仍泄漏 36 字节。
- AP-2 的改动不新增分配，alias 清空是 O(1)；AP-1 的栈 uuid 少一次堆分配；Pi 的 owned uuid 多一次 clone，但会在释放路径回收。
- 三者都没有可测量的性能回归，也没有新增依赖或协议字段。

### 4.4 遗留问题

- **AP-1** 在报告里额外指出两个预存在问题：
  1. 自定义 `context.allocator` 下 `json.destroy_value` 处理 `json.Object` 会崩，导致回归测试无法覆盖工具调用；
  2. `ODIN_TEST_TRACK_MEMORY=true` 时 `test_loop_blobs_large_tool_output` 会报 `bad free`，疑似 fake provider 的 args 树与销毁 allocator 不匹配。
- **AP-2** 额外指出 uuid 泄漏，并询问是否一起处理；但没有修。日志里还探索了一个“污染 7 字节 free 会段错误”的异常，最终判断为堆布局/地址复用伪影并放弃，**没有写进最终报告**。这不是本次 UAF 的结论，但说明它的核实阶段有一次未收敛的支线。
- **Pi** 没有继续追这两个预存在问题，但它的测试已经覆盖 tool call 路径，实际修复的验证更完整。

## 6. 总结

三个运行最终都正确修掉了同一个 UAF，差异主要在过程效率、测试覆盖和修复完整性：

- **Pi 的优势**：有效工作最省时（265.2s）、token 最低（2.49M）；修复方案防御性最好（clone-before-delete、end-id 补齐）；一个回归测试覆盖三条关键路径；文档同步完整。**综合仍是本次最好。**
- **AP-2 的优势**：修复阶段最快（125.4s，扣掉前端环境约 47s）；工具次数最少（61）；总 token 只比 Pi 高约 8%，比 AP-1 低约 49%。**如果只看“根因已确认后的修复”，AP-2 最好。**
- **AP-2 的代价**：verify 阶段在 52s 就拿到证据，却被一个次要 allocator 异常多拖了约 138s，报告到 231.6s 才出来；回归测试不覆盖自动生成 id 和 tool call；uuid 泄漏只报告未修；文档未同步；而且它把“核实一下”自行扩展成了修复，用户没有确认机会。
- **AP-1 的优势**：核实最快（90.5s）；动态证明直接；报告额外指出两个预存在问题；文档对单一属主模型的描述更集中。**如果看核实证据和报告完整度，AP-1 最好。**
- **AP-1 的代价**：fix 阶段在自定义 allocator / `json.destroy_value` 上陷入约 138s，导致总时间约为 Pi 的 1.8 倍，token 约为 2.1 倍；回归测试没有覆盖工具调用路径。

两个 AP 运行说明单次样本的方差很大：同一个模型、同一套工具，AP-1 和 AP-2 的总时间差 1.35 倍、token 差 1.96 倍，主要差别不是模型能力，而是“什么时候停止支线调查”。如果以 **“用最少的时间和 token 得到正确且可回归的修复”** 为标准，本次对比 **Pi 更好**；如果以 **“修复阶段的速度”** 为标准，**AP-2 更好**；如果以 **“核实证据的充分性和报告的完整性”** 为标准，**AP-1 更好**。
