## 4. 优化效果对比

### 4.1 修复方案

两者都从同一个父提交 `e5575ba` 出发，核心修法几乎一致：

| 点 | AP | Pi |
| --- | --- | --- |
| 拆分释放职责 | `loop_release_owned` → `loop_release_message_id` + `loop_release_calls` | `loop_release_owned` → `loop_release_calls`；`owned` 自己 retained |
| `loop_own_calls` | 只调用 `loop_release_calls` | 只调用 `loop_release_calls` |
| id 统一写入 | 新增 `loop_set_message_id`（先释放、再 clone、再让 current 别名 owned） | 新增 `loop_own_message_id`（先 clone、再 delete 旧值） |
| 无 provider id | 改用 `uuid.to_string_buffer` 栈缓冲，再 clone 给 owned | 生成的 uuid 直接赋给 `owned_message_id` |
| `Message_End` 补 id | 未专门处理（start 已生成 uuid，保持 current） | `current` 为空时才用 `ev.message_id` 补齐 |
| 文档 | 修改 architecture 所有权段落 + react-loop 一句 | architecture 新增第 5 条 + react-loop 一句 |

两者都修掉了根因：`Provider_Message_End` 不再提前释放 `message_id`；也顺带修掉了“provider 不给 id 时 uuid 泄漏”。

实现细节上：

- AP 的 `loop_set_message_id` 把“释放 + clone”集中到一个入口，所有权模型更集中、注释清楚；但它是“先释放旧值，再 clone 新值”，如果未来某个调用把 `owned_message_id` 本身传回来，会有 self-alias 风险。当前调用点不会触发。
- Pi 的 `loop_own_message_id` 明确“clone 早于 delete”，并为 `Message_End` 补了“current 为空才采纳 end id”的分支，防御性更强；代价是多一个函数和一点分支逻辑。

### 4.3 对运行时行为/性能的影响

两者都只改 `ap-core/engine/loop.odin` + 测试 + 文档，不涉及协议和前端：

- `message_end` 路径少了一次对 `owned_message_id` 的释放，其他行为不变；
- transcript 中 `message_start` / `message_end` 的 id 重新一致，修复了 Web 端 `hadDelta[messageId]` 查不到、可能重复追加气泡的问题；
- 修复了 provider 不返回 id 时的每次消息泄漏（AP 用栈缓冲，Pi 用 owned 持有）；
- 没有可测量的性能回归，也没有新增依赖或协议字段。

### 4.4 遗留问题

AP 在报告里额外指出两个未改的问题：

1. 自定义 `context.allocator` 下 `json.destroy_value` 处理 `json.Object` 会崩，导致回归测试无法覆盖工具调用；
2. `ODIN_TEST_TRACK_MEMORY=true` 时 `test_loop_blobs_large_tool_output` 会报 `bad free`，疑似 fake provider 的 args 树与销毁 allocator 不匹配。

这两个都是预存在问题，AP 明确标注“未改，供你判断”，信息量更足。Pi 没有继续追这两个预存在问题，但它的测试已经覆盖了 tool call 路径，实际修复的验证更完整。

## 6. 总结

两个 agent 最终都正确修掉了同一个 UAF，修复思路高度相似，差异主要在过程效率与测试覆盖：

- **AP 的优势**：核实快；动态证明直接；报告额外指出两个预存在问题；文档对单一属主模型的描述更集中。
- **AP 的代价**：修复阶段在自定义 allocator / `json.destroy_value` 上陷入较深，导致总时间约为 Pi 的 1.7 倍，token 约为 2.1 倍；回归测试没有覆盖工具调用路径。
- **Pi 的优势**：整体更省时省 token；修复方案防御性更好（clone-before-delete、end-id 补齐）；一个回归测试覆盖三条关键路径，并且验证了旧代码变红。
- **Pi 的不足**：核实阶段尝试了多种复现手段才成功，前期较慢；没有继续追预存在的 `bad free` 和 allocator 兼容性问题。

如果以 **“用最少的时间和 token 得到正确且可回归的修复”** 为标准，本次对比 **Pi 更好**。  
如果以 **“核实证据的充分性和报告的完整性”** 为标准，**AP 更好**。
